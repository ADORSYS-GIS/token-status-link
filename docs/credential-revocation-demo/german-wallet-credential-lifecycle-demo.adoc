= German Wallet PID Verification, Issuance, and Revocation Setup
:toc:
:toclevels: 3

== Purpose

This document describes the configuration required to demonstrate the following flow with the German National Wallet Sandbox:

. The wallet presents an emulated German PID to Keycloak during issuance.
. Keycloak validates the PID and issues a verfiable Credential.
. The wallet presents that issued credential to authenticate to Keycloak.
. The credential is revoked through the Token Status plugin.
. A later presentation of the revoked credential is rejected.

The documented configuration has been validated with Keycloak `26.8.0`. It is not a general compatibility statement for other Keycloak versions.

== Architecture and responsibilities

[cols="1,3",options="header"]
|===
|Component |Responsibility

|Keycloak 26.8.0
|Acts as the OpenID4VCI Credential Issuer and the OpenID4VP Verifier.

|keycloak-oid4vp-plugin
|Creates the wallet authorization request, validates PID and credential presentations, and enforces revocation during login.

|token-status-link
|Adds a status reference to issued credentials and synchronizes revocation with a Status List server.

|Status List server
|Publishes credential status information consulted during presentation verification.

|keycloak-oid4vc-mock-fe
|Provides a test application for creating offers, viewing issued credentials, and requesting revocation.

|German National Wallet Sandbox
|Holds the emulated PID and the issued `IdentityCredential`.
|===

== Prerequisites

Before starting the setup, ensure that the following conditions are met:

* Java 21, Maven, Node.js, Docker, and OpenSSL are available.
* The German National Wallet Sandbox account is active and contains the emulated PID.
* Keycloak is reachable by the mobile wallet through a stable public HTTPS endpoint.
* Access and registration certificates have been issued for the Sandbox organization.
* Test certificates, private keys, keystores, and wallet identities are used. Do not use production material.

Set paths that match the local workspace:

[source,bash]
----
export WORKSPACE="$HOME/Projects"
export DEPLOYMENT="$WORKSPACE/keycloak-oauth-sig/oid4vci-deployment"
export STATUS_PLUGIN="$WORKSPACE/token-status-link"
export VP_PLUGIN="$WORKSPACE/keycloak-oid4vp-plugin"
export MOCK_FE="$WORKSPACE/keycloak-oid4vc-mock-fe"
export REALM=oid4vc-vci
export PUBLIC_KEYCLOAK_URL=https://<public-keycloak-host>
----

== Obtain and configure Sandbox trust material

The German Wallet does not trust a verifier or issuer merely because it exposes an HTTPS endpoint. It evaluates the EUDI trust material included in the request and issuer metadata. Certificate configuration is therefore a prerequisite for both PID presentation and credential issuance.

Follow these procedures in order:

. https://github.com/ADORSYS-GIS/keycloak-oid4vp-plugin/blob/main/docs/modules/ROOT/pages/obtaining-sandbox-access-and-registration-certificates.adoc[Obtain Sandbox access and registration certificates].
This procedure covers the German EUDI Wallet Sandbox Registrar and the certificate content required for verifier and issuer registration.
. https://github.com/ADORSYS-GIS/token-status-link/blob/main/docs/eudi-access-certificate.md[Configure the access certificate and issuer registration certificate in Keycloak].
This procedure imports the private key and access-certificate chain into a Keycloak keystore provider, configures the active signing key, and publishes the issuer registration certificate in signed Credential Issuer Metadata.

The required material serves separate purposes:

[cols="1,3",options="header"]
|===
|Material |Why it is required

|Access certificate and matching private key
|Keycloak signs Credential Issuer Metadata and OpenID4VP request material with this key. The wallet uses the certificate chain to identify the Sandbox organization behind the signature.

|Verifier registration certificate
|Authorizes the verifier to request the PID data and the credential type used for wallet login. The wallet checks the certificate before allowing disclosure.

|Issuer registration certificate
|Identifies the issuer and declares the credential type it is authorized to issue. Keycloak publishes it through the `issuer_info` metadata claim.
|===

For this scenario, create the verifier registration certificate with these entries:

* Select the *PID (EU)* schema, not the legacy *PID* schema.
* Request document type `eu.europa.ec.eudi.pid.de.1`.
* Include `given_name` and `family_name`, because the PDI profile requests and binds these values.
* Include e.g`IdentityCredential`, because the same wallet later presents it for login.

Create an issuer registration certificate that authorizes issuance of `IdentityCredential` and configure it through `oid4vci.issuer_info` as described in the certificate configuration guide.

Use `x509_hash` as the OpenID4VP client identifier prefix. The Sandbox access certificates used for this environment do not reliably provide a DNS Subject Alternative Name, so `x509_san_dns` is not suitable. Ensure that the Keycloak signing key associated with the access certificate is the only active ES256 signing key used for this flow.

== Provide a public HTTPS endpoint

The mobile wallet must retrieve Keycloak metadata and request URIs from the device. A Keycloak URL that is only reachable as `localhost` from the development machine cannot be used.

Use any HTTPS-capable ingress appropriate for the environment, for example:

* A DNS name behind a reverse proxy.
* A controlled development or test environment with a publicly trusted TLS certificate.
* A secure development tunnel.

Ngrok was used during local validation because it exposes a locally running HTTPS Keycloak instance to the physical mobile device without deploying Keycloak to a remote host. It is an example only, not a required component and not a production deployment model.

[source,bash]
----
# Optional local-development example. Replace with the selected public HTTPS endpoint.
ngrok http https://localhost:8443
export PUBLIC_KEYCLOAK_URL=https://<ngrok-host>
----

The chosen public URL must remain stable for a complete test run and must be used consistently in Keycloak hostname settings, issuer metadata, request URIs, and the mock frontend configuration.

== Install the Keycloak providers

Build the Token Status and OpenID4VP plugins from the versions being tested, then install one JAR for each provider into the deployment's `providers` directory.

[source,bash]
----
cd "$STATUS_PLUGIN"
git checkout main && git pull --ff-only
./mvnw clean package -DskipTests

cd "$VP_PLUGIN"
git checkout main && git pull --ff-only
./mvnw clean package -DskipTests

mkdir -p "$DEPLOYMENT/providers"
rm -f "$DEPLOYMENT"/providers/keycloak-token-status-plugin-*.jar
rm -f "$DEPLOYMENT"/providers/keycloak-oid4vp-plugin-*.jar
cp "$STATUS_PLUGIN"/target/keycloak-token-status-plugin-*.jar "$DEPLOYMENT/providers/"
cp "$VP_PLUGIN"/target/keycloak-oid4vp-plugin-*.jar "$DEPLOYMENT/providers/"
----

Restart Keycloak after replacing a provider JAR. Keeping stale JARs in the provider directory can result in loading an unintended implementation.

== Start the validated Keycloak deployment

Create `config.override.yaml` in `oid4vci-deployment`. The managed-realm configuration enables creation of the OpenID4VP authentication flow for `oid4vc-vci`.

[source,yaml]
----
keycloak:
  version: "26.8.0"
  enable_preauth_code: true
  enable_rest_credential_offer: true
  enable_credential_offer_create: true
start_command: "start --hostname=${PUBLIC_KEYCLOAK_URL} --hostname-strict=false --proxy-headers=xforwarded --https-port=${KEYCLOAK_HTTPS_PORT} --https-certificate-file=${SSL_SERVER_CERT} --https-certificate-key-file=${SSL_SERVER_KEY} --log-level=INFO,io.github.adorsysgis.keycloakstatuslist:DEBUG,io.github.adorsysgis.keycloak.protocol.oid4vc:DEBUG --spi-realm-restapi-extension-oid4vp-auth-managed-realms=oid4vc-vci"
----

[source,bash]
----
cd "$DEPLOYMENT"
./keycloak-ssi.sh setup -d
./keycloak-ssi.sh config
----

== Configure credential issuance and status publication

Set the following realm attributes in the deployment realm configuration and apply them with `./keycloak-ssi.sh config`:

[cols="1,3",options="header"]
|===
|Attribute |Purpose and value

|`oid4vci.presentation_during_issuance`
|Set to `true` to require the nested OpenID4VP PID presentation before credential issuance.

|`oid4vci.signed_metadata.alg`
|Set to `ES256`, matching the access-certificate signing key.

|`oid4vci.issuer_info`
|Set to the JSON array that contains the issuer registration-certificate JWT.

|`status-list-enabled`
|Set to `true` to publish credential status through the Token Status plugin.

|`status-list-server-url`
|Set to the selected HTTPS Status List server, for example `https://statuslist.eudi-adorsys.com`.
|===

[source,json]
----
[
  { "format": "registration_cert", "data": "<issuer-registration-certificate-jwt>" }
]
----

The following attributes are Sandbox compatibility settings. They are not production defaults and must be assessed before use outside the Sandbox:

[source,text]
----
oid4vci.allow_proof_iss_mismatch=true
oid4vci.omit_encryption_metadata=true
----

Configure e.g`IdentityCredential` to require the PDI profile and disclose the status claim:

[source,text]
----
vc.requires_presentation: nested_oid4vp_flow
vc.presentation_profile_id: nested-presentation-during-issuance
vc.credential_build_config.sd_jwt.visible_claims: id,iat,nbf,exp,jti,status,sub
----

Add the `oid4vc-status-list-claim-mapper` protocol mapper to the credential scope. The mapper creates the status-list reference; `visible_claims` permits that reference to be included in the issued SD-JWT. Both are required for revocation to be enforced later by the verifier.

== Configure PID verification and wallet login

Configure a PDI profile named `nested-presentation-during-issuance` with these requirements:

[cols="1,3",options="header"]
|===
|Profile property |Value

|Identity source
|`session`

|Credential format
|`mso_mdoc`

|Credential type
|`eu.europa.ec.eudi.pid.de.1`

|Requested claims
|`eu.europa.ec.eudi.pid.1/given_name` and `eu.europa.ec.eudi.pid.1/family_name`

|Binding rules
|Compare `given_name` with `firstName` and `family_name` with `lastName` using `claim_equals_user_attribute`.

|Trust mechanism
|`eudi_pid_trust_list`, configured with the EUDI PID test trust list and its signing certificate.
|===

The Keycloak user accepting the offer must match the PID claims exactly. For the standard Sandbox fixture, use username `erika`, first name `ERIKA`, and last name `MUSTERMANN`. A different value causes the binding rule to reject the PID presentation.

Configure the OpenID4VP authenticator used for both PDI and wallet login:

[cols="1,3",options="header"]
|===
|Setting |Value

|Client identifier prefix
|`x509_hash`

|Response mode
|`direct_post.jwt`

|Request URI method
|`get`

|Custom URL scheme
|`openid4vp://`

|Access certificate
|Base64-encoded DER body of the Sandbox access certificate.

|Registration certificate
|Verifier registration-certificate JWT.

|Holder binding
|Enabled, with a maximum proof age of 60 seconds.

|Revocation enforcement
|Reject revoked credentials enabled; allow credentials without a status claim disabled.

|Login theme
|`keycloak.v2+oid4vp`
|===

Configure the standard `identity-login` profile for self-trusted `IdentityCredential` login. The verifier registration certificate must include `IdentityCredential`, otherwise the wallet will not authorize this later presentation.

== Configure the test application

Configure `keycloak-oid4vc-mock-fe` to create authorization-code offers. PDI is not performed through the pre-authorized offer path.

[source,dotenv]
----
VITE_KEYCLOAK_URL=https://<public-keycloak-host>
VITE_KEYCLOAK_REALM=oid4vc-vci
VITE_KEYCLOAK_CLIENT_ID=oid4vc-demo-public
VITE_OID4VC_DEFAULT_CREDENTIAL_CONFIGURATION_ID=IdentityCredential
VITE_OID4VC_PRE_AUTHORIZED=false
VITE_BASE_PATH=/
----

For `oid4vc-demo-public`, configure `http://localhost:4200/*` as a valid redirect URI and `http://localhost:4200` as a web origin. Enable `oid4vci.enabled` for this client and assign `IdentityCredential` as an optional client scope.

== Verify the end-to-end flow

=== Issue after PID presentation

. Sign in to the mock frontend as `erika`.
. Create an authorization-code offer for `IdentityCredential`.
. Open the offer in the German Wallet and approve the nested OpenID4VP request.
. Select the PID (EU) credential and authorize disclosure of `given_name` and `family_name`.
. Confirm issuance and verify that `IdentityCredential` is added to the wallet.

=== Authenticate with the issued credential

. Sign out of the mock frontend.
. Start a new login and select the Identity Wallet option.
. Present `IdentityCredential` and approve the request.
. Verify that the mock frontend dashboard opens.

=== Revoke and verify rejection

. In the mock frontend, open Credentials, select the issued credential, and revoke it with a test reason.
. Confirm that the displayed credential status changes to `Revoked`.
. Sign out, start another Identity Wallet login, and present the revoked credential.
. Verify that Keycloak rejects the login.

== Troubleshooting

[cols="1,3",options="header"]
|===
|Symptom |Likely cause and correction

|The wallet cannot resolve metadata or the request URI.
|Keycloak is not reachable from the device, or the public URL differs between the hostname, metadata, request object, and frontend. Use one stable public HTTPS URL throughout the test.

|The wallet rejects the PID request.
|The verifier registration certificate does not authorize the requested PID type or fields. Verify *PID (EU)*, `eu.europa.ec.eudi.pid.de.1`, `given_name`, and `family_name`.

|PID binding validation fails.
|The Keycloak user's `firstName` or `lastName` does not exactly match the presented PID claim.

|The wallet cannot use issuer metadata.
|The access certificate, matching Keycloak signing key, issuer registration certificate, or `issuer_info` configuration is missing or inconsistent. Re-run the linked certificate configuration procedure.

|A revoked credential is accepted during login.
|The credential was issued without the status mapper or visible `status` claim, the Status List server was not updated, or revocation enforcement is disabled in the authenticator.
|===

== Security considerations

* Keep private keys, PKCS12 files, registration certificate JWTs, and their passwords out of source control.
* Do not enable `status-list-tls-trust-all` outside a disposable local test environment.
* A development tunnel exposes a local service to the internet. Restrict access and never expose production keys, real identities, or production credentials through it.
